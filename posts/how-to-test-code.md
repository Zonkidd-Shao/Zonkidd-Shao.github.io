很多开发者把测试当成"上线前的负担"，但实际上，**测试是开发流程的一部分**——它帮你提前暴露问题、建立信心、让重构变得安全。

## 测试金字塔

经典的测试策略是"金字塔"结构：

```
        /\
       /  \        端到端测试（少）
      /    \
     /------\
    /        \     集成测试（适中）
   /          \
  /------------\
 /              \  单元测试（多）
/----------------\
```

- **底层（单元测试）**：最多、最快、最稳定，测试单个函数/组件
- **中层（集成测试）**：验证模块间协作
- **顶层（端到端测试）**：最少、最慢，模拟真实用户路径

## 一个可落地的测试示例

以 JavaScript 为例，用单元测试验证一个工具函数：

```js
// utils/format.js
export function formatPrice(value) {
  if (typeof value !== 'number' || !Number.isFinite(value)) {
    throw new TypeError('price must be a finite number');
  }
  return `¥${value.toFixed(2)}`;
}
```

```js
// utils/format.test.js
import { describe, it, expect } from 'vitest';
import { formatPrice } from './format';

describe('formatPrice', () => {
  it('格式化为两位小数', () => {
    expect(formatPrice(9.5)).toBe('¥9.50');
  });

  it('处理整数', () => {
    expect(formatPrice(100)).toBe('¥100.00');
  });

  it('非法输入抛出异常', () => {
    expect(() => formatPrice('9.5')).toThrow(TypeError);
  });
});
```

## 测试的黄金法则

| 法则 | 说明 |
| --- | --- |
| **先写测试** | 用测试驱动开发（TDD），先定义"正确"再实现 |
| **测试行为，而非实现** | 别依赖内部细节，否则改代码就崩测试 |
| **覆盖关键路径** | 边界条件、错误分支、主流程至少各一个用例 |
| **保持快速** | 慢的测试会被跳过，快的测试才会被运行 |

## 什么时候测什么

- **工具函数**：单元测试，覆盖输入输出
- **接口**：集成测试，验证数据流
- **页面流程**：端到端测试，走关键用户路径

> 测试的投入产出比极高——修复一个线上 bug 的成本，往往是写测试的十倍。

最后，让测试成为 CI 的一部分：每次提交自动运行，失败就阻断合并。**让质量成为默认选项，而不是例外。**
